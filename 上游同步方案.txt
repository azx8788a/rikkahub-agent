五、当前问题：语义混合

-X ours 的规则：文本冲突处保留我方，不冲突处自动并入上游。但代码是整体，出现错位：
- 上游新代码调用了上游新接口，但接口定义所在位置冲突、被我们旧版覆盖
- 我们保留的旧代码和上游自动并入的新代码在同一文件里不匹配

最新 CI 运行编号 38725532093（提交 f079d3c2），在 :ai:compileReleaseKotlin 失败，报 29 个错误，全集中在 4 个文件：

  文件 1：ProviderSetting.kt（18 条错误）
  我们有 6 个自定义模型提供商类（AICore、LiteRtLocal、LlamaCppLocal、Codex、Grok、
  GeminiOAuth）来自 ExTV fork。上游在基类中新增了 abstract val customHeaders 
  和 copyProvider 的 customHeaders 参数（已自动并入接口定义处）。但这 6 个类没有
  override customHeaders，copyProvider 签名也缺少 customHeaders 参数。
  
  文件 2：util/Request.kt（4 条错误）
  上游在此文件新增了 mergeCustomHeaders 扩展函数（fun ProviderSetting.mergeCustomHeaders()），
  但文件顶部缺少 import me.rerere.ai.provider.ProviderSetting，导致 ProviderSetting 类型
  无法解析，进而链式引发 customHeaders、name 字段和 toHeaders 调用均报错。

  文件 3：OpenAIProvider.kt（3 条错误，toHeaders 引用）
  上游在 OpenAIProvider.kt 中把 import me.rerere.ai.util.toHeaders 换成了
  import me.rerere.ai.util.mergeCustomHeaders，但我方保留的 3 处代码仍调用
  params.customHeaders.toHeaders()，缺少对应 import。

  文件 4：OpenAIProvider.kt（3 条错误，ImageEditParams.size）
  上游新增函数 editImageWithInputReferences 使用了 params.size 字段，
  但 Provider.kt 的 ImageEditParams 结构保留了我方的旧字段 aspectRatio，
  没有 size 字段。此为"语义决策点"。

七、修复方案

策略：保留当前的 -X ours 合并产物，按模块逐层修，不重做合并。
理由：我方定制量大（代理功能成体系），重做成本远高于修补。
每文件裁决三选一：
  a. 我方无定制的文件：直接取上游整版
  b. 双方都有改动：手工融合（以我方为主、补上游新接口）
  c. 逻辑冲突严重：以我方为准，记录备忘

执行顺序：
  第 1 批：ai 模块（12 个交叉文件，目前 29 个已知错误全在此）
    1. ProviderSetting.kt：给 6 个自定类补 customHeaders + copyProvider 参数（机械）
    2. util/Request.kt：补 import me.rerere.ai.provider.ProviderSetting
    3. OpenAIProvider.kt：补 import me.rerere.ai.util.toHeaders
    4. OpenAIProvider.kt ImageEditParams：两字段短期并存方案——
       在 ImageEditParams 加 val size: String = "auto"（上游新函数用）；
       保留 aspectRatio（我方旧路径继续用）；不加 ImageGenSize 枚举（用裸字符串），
       避免新增依赖环路。此为最小改动，两端代码均编译通过，语义无冲突。
    5. 扫其余 ai 交叉文件，同类问题一并修。
    6. 静态自检（引用/import/签名），推送 CI。
  第 2 批：app 模块（124 个交叉文件）
    按功能簇分批：数据层（DB schema 迁移、设置存储）→ 核心服务（消息生成、
    压缩摘要、工具系统）→ 界面层（MD3 改版几十个页面 + 我方 agent 入口接回）。
    每批提交一次 CI。
    ImageEditParams 后续影响：若 app 侧 ImgGenVM 编译因 size/aspectRatio 报错，
    一并适配（短期两字段共存不会引发编译问题；如后续决定统一，再专项处理）。
  第 3 批：workspace、search 等其余模块。
  第 4 批：CI 全绿 → 产 APK → 真机验收（重点：压缩摘要、agent 工具、本地模型）。

八、关键决策说明

  决策 4（ImageEditParams）：不选"全面采用上游 size 方案"的原因——
  上游 size 依赖 ImageGenSize 枚举（定义在 ai/ui/Image.kt，该文件在我方
  树未合并、上游的 size 相关 app UI 也未并入），全面改造需同时动 ai 和
  app 两个模块，约 10+ 文件、涉及界面改动，跨模块风险大。用两字段短期
  共存方案，编译通过后，后续可择机统一（那时上游相关界面代码也一起评估）。
